# Vehicle Lamp ECU — 시스템 요구사항 (SYS.2)

> **상태: 초안 v0.2 (CAN 구조 반영, 검토 중).** 결정 D-01~D-15를 정리했다. CAN 전환으로 재검토할 요구사항은 확정 전이며 구현·시험은 미수행.

## 1. 시스템 범위 및 입출력

- **BCM 시뮬레이터:** Arduino UNO Q가 물리 스위치(IGN, 방향 레버, 비상등 버튼, 미등, 브레이크, R/NOT R)를 받아 입력을 안정화·해석한 뒤 CAN으로 명령을 전송한다.
- **후방 램프 ECU:** STM32F103C8T6이 CAN 명령을 수신하여 램프 출력·점멸·PWM·진단을 제어한다. MCU 전원은 IGN OFF에도 유지한다.
- **통신:** UNO Q ↔ CAN 트랜시버 ↔ Classical CAN ↔ CAN 트랜시버 ↔ STM32F103. CAN FD는 확장 검토 대상이다.
- **출력:** 후방 좌/우 방향지시등(`TURN_L/R`), 좌/우 미등·제동등 공용(`TAIL_STOP_L/R`), 후진등(`REVERSE_LAMP`), 중앙 보조제동등(`CHMSL`: 적색 LED 3개를 하나의 독립 채널로 제어).
- **검증:** PC SIL과 UNO Q 기반 Custom HIL로 CAN 메시지 처리 및 실제 출력 파형을 시험한다. UNO Q의 BCM 시뮬레이션과 HIL 계측 역할을 구분하여 설계한다.
- **제외:** 전방 램프(전방 방향지시등 포함), 자동 미등(AUTO), 전체 P-R-N-D 모델, 실제 LED 단선·단락 자동 감지, 양산 ECU 기능안전 및 인증.

실제 핀 번호, LED 구동 회로, CAN 트랜시버·종단저항, UNO Q의 HIL 계측 연결은 **SYS.3**에서 정한다.

## 2. 시스템 요구사항

각 요구사항의 `D-xx`는 [설계 결정 기록](decision-log.md)에 연결된다. 기존 램프 기능 기준은 보존했지만, 물리 스위치 → CAN 경로로 바뀌면서 **담당 노드·타이밍·오류 처리의 검토가 필요하다.**

### 2.1 방향지시등·비상등

| ID | 요구사항 (시험 가능 조건) | 근거 |
|---|---|---|
| SYS-001 | IGN ON·비상등 OFF 명령에서 방향 레버가 우측이면 후방 우측만, 좌측이면 후방 좌측만 점멸하고 OFF이면 양쪽 방향지시등이 OFF여야 한다. | D-01, D-04 |
| SYS-002 | UNO Q는 비상등 버튼의 유효한 눌림 한 번을 비상등 상태 전환 한 번으로 처리하고, STM32에 CAN으로 비상등 상태를 전달해야 한다. | D-04, D-09 |
| SYS-003 | 비상등 ON이면 IGN·레버 상태에 관계없이 후방 좌우 방향지시등이 같은 위상으로 점멸해야 하며 비상등이 방향 레버보다 우선한다. | D-05, D-06 |
| SYS-004 | 안정적으로 계속 점멸 중인 방향지시등/비상등은 ON 구간과 OFF 구간 각각 400±20ms여야 한다. 기능 전환으로 중간에 끊긴 구간은 제외한다. | D-07 |
| SYS-005 | 좌·우 방향지시/비상등 등 활성 점멸 기능이 변경되면 새 점멸 기능은 ON부터 시작하고 타이머를 초기화해야 한다. | D-07 |
| SYS-006 | **재검토:** 기존 '스위치→STM32 첫 출력 20ms' 기준은 직접 입력 구조에서 정의했다. CAN 경로의 입력→출력 시간 목표 및 측정 조건을 새로 확정해야 한다. | D-09, D-13 |
| SYS-007 | **재검토:** 기존 '비상등 버튼→STM32 첫 출력 30ms' 기준은 직접 입력 구조에서 정의했다. UNO Q 처리·CAN 전송·STM32 제어를 포함한 시간을 다시 정해야 한다. | D-09, D-13 |

### 2.2 미등·제동등·후진등

| ID | 요구사항 (시험 가능 조건) | 근거 |
|---|---|---|
| SYS-008 | IGN과 무관하게 미등·브레이크 입력의 4가지 조합에서 좌우 공용 램프와 CHMSL이 아래 진리표대로 작동해야 한다. | D-03, D-05, D-06, D-10, D-11 |
| SYS-009 | 미등만 ON인 공용 출력의 PWM은 듀티 18~22%(목표 20%), 주파수 950~1,050Hz(목표 1kHz)여야 한다. 브레이크 ON의 100%는 연속 점등이다. | D-11 |
| SYS-010 | IGN ON에서 후진 스위치가 R이면 후진등 ON, NOT R이면 OFF이며 다른 허용된 램프 기능과 동시에 작동해야 한다. | D-02, D-05 |
| SYS-011 | IGN OFF에서는 일반 방향지시와 후진등 출력을 차단하지만, 비상등·미등·제동등·CHMSL은 해당 유효 입력 조건대로 작동해야 한다. | D-06 |

**공용 미등·제동 출력 진리표** (IGN ON/OFF 모두 동일, 가상 고장 없음)

| 미등 | 브레이크 | TAIL_STOP_L/R | CHMSL |
|---|---|---|---|
| OFF | OFF | OFF (0%) | OFF |
| ON | OFF | PWM 20%, 1kHz | OFF |
| OFF | ON | 연속 ON (100%) | ON |
| ON | ON | 연속 ON (100%) | ON |

### 2.3 시동·초기화·오류 입력

| ID | 요구사항 (시험 가능 조건) | 근거 |
|---|---|---|
| SYS-012 | MCU 전원이 계속 유지되는 상태에서 IGN OFF/ON 전환만으로 비상등 토글 상태가 바뀌어서는 안 된다. | D-12 |
| SYS-013 | IGN OFF→ON 상태가 CAN으로 반영되면, 이미 전달된 방향 레버·R 명령은 스위치를 재조작하지 않아도 출력에 반영돼야 한다. | D-12 |
| SYS-014 | IGN OFF에도 MCU는 전원이 공급되어 허용된 비상등·미등·제동등을 처리할 수 있어야 한다. | D-06, D-12 |
| SYS-015 | STM32 초기화 중 모든 램프 출력은 OFF여야 한다. 초기화 후 수신된 CAN 명령을 반영한다. **재검토:** 기존 D-08의 '물리 입력 재평가·비상등 토글 OFF'는 토글 상태가 UNO Q에 있으므로 재부팅 시 동작을 별도 정의해야 한다. | D-08 |
| SYS-016 | 좌/우 방향지시 명령이 동시에 활성화된 잘못된 CAN 입력을 받으면 일반 방향지시 요청을 무효 처리하고 오류를 기록해야 한다. 비상등과 다른 정상 램프 기능은 유지해야 한다. | D-08 |

### 2.4 시험용 가상 고장

| ID | 요구사항 (시험 가능 조건) | 근거 |
|---|---|---|
| SYS-017 | 시험 빌드에서 UNO Q의 별도 UART 명령으로 지정 출력에 가상 고장을 설정/해제할 수 있어야 한다. SIL은 UART 없이 동일한 내부 고장 처리 로직을 호출한다. | D-08, D-14 |
| SYS-018 | 가상 고장으로 지정한 출력 채널만 강제로 OFF 처리하고, 다른 정상 채널 출력은 기존 규칙대로 유지해야 한다. | D-14 |
| SYS-019 | 가상 고장 상태는 명시적 CLEAR 명령까지 유지하고, 해제하면 현재 유효 입력에 따라 해당 출력 상태를 재평가해야 한다. | D-14 |
| SYS-020 | 오류 이벤트는 코드·채널·발생/해제·시간을 포함해 RAM에 최근 16건까지 기록하고, 초과 시 오래된 이력을 덮어써야 한다. MCU 재부팅 시 RAM 오류 이력과 가상 고장 상태는 초기화돼야 한다. | D-08, D-14 |

> SYS-017~020은 **테스트를 위한 고장 모사**이며, 실제 LED 고장 감지나 실차의 안전 상태를 증명하지 않는다.

### 2.5 BCM–CAN–후방 램프 ECU (추가 검토 대상)

| ID | 요구사항 초안 | 근거 |
|---|---|---|
| SYS-021 | UNO Q(BCM 시뮬레이터)는 스위치의 유효 상태를 Classical CAN 명령으로 STM32 ECU에 전달해야 한다. | D-15 |
| SYS-022 | STM32 ECU는 수신한 CAN 명령을 검사하고 유효한 명령에 따라 기존 램프 기능을 제어해야 한다. | D-15 |
| SYS-023 | 통신 프레임 누락·잘못된 데이터·장시간 무수신을 검출하고 정해진 상태로 처리해야 한다. **타임아웃·출력 정책은 SYS.2에서 결정 예정.** | D-15 |

**CAN FD 확장:** UNO Q 측에는 FDCAN 하드웨어가 있지만 STM32F103 내장 CAN은 Classical CAN까지만 지원한다. CAN FD 시험에는 STM32 측 SPI 외장 CAN FD 컨트롤러(예: MCP2518FD)·FD 지원 트랜시버 추가 또는 MCU 교체가 필요하다. Classical CAN 구현과 CAN FD 구현은 별도 검증 항목이다. 일반 CAN FD와 조명용 CAN FD Light를 혼동하지 않는다.

## 3. 소프트웨어 단계(SWE.1)로 넘길 구현 세부 기준

SYS.2는 외부에서 확인 가능한 결과를 중심으로 작성했다. 내부 처리 방식은 **SWE.1**에서 요구사항으로 구체화한다.

| 이미 결정한 SW 세부 기준 | 근거 |
|---|---|
| UNO Q의 스위치 디바운싱: 비상등·IGN 20ms, 방향 레버·미등·후진 10ms, 브레이크 5ms | D-09, D-15 |
| ECU의 유효 CAN 명령 수신 이후 출력 응답시간은 재검토. 기존 SW 10ms·E2E 20/30ms 기준과 구별 | D-13, D-15 |
| 테스트용 UART 진단 명령, RAM 오류 16건 및 CLEAR 처리 | D-14 |
| 점멸 상태머신·우선순위·PWM 타이머·시동 상태 전환 처리 | D-05~D-12 |

## 4. 검증 방향 및 남은 검토

- **SIL(예정):** 입력 조합, 우선순위, 디바운싱·타이밍, 가상 고장 상태와 로그를 PC에서 검증한다.
- **HIL(예정):** UNO Q로 STM32 입력을 생성하고 GPIO 점멸 시간, 첫 점등 시간, PWM 주파수·듀티, 고장 설정·해제를 관측한다.
- **검토 예정:** CAN 명령·전송 주기·통신 이상 시 출력 정책, ECU 리셋 후 상태 동기화, E2E 응답시간, HIL 측정 해상도/전압 조건(SYS.3). 실제 회로·코드·테스트가 없는 상태에서는 PASS라고 표시하지 않는다.

**SYS.2 완료 조건:** 기존 20개 요구사항과 통신 요구를 검토하고, 변경된 역할·시간 기준과 통신 오류 정책을 확정한다. 지금은 아직 **미완료**다.
