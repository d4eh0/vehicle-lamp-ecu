# SYS.2를 정할 때 했던 고민

SYS.2에서는 숫자 하나, 비정상 입력 하나가 실제 테스트 조건이 되는 게 어려웠다. 최종 합의는 `docs/[SYS.2]system-requirements.md`; 여기는 왜 그렇게 정했는지를 기억하기 위한 노트다.

## 시스템 경계부터 다시 고민했다

- ECU 하나의 시스템 요구사항을 쓰는 건지, UNO Q와 STM32를 합친 장비 전체를 쓰는 건지 애매했다. 처음 초안엔 UNO Q의 버튼 디바운싱까지 SYS 요구사항으로 들어가 있었다.
- UNO Q는 **외부 BCM 시뮬레이터**, STM32가 **Rear Lamp ECU**. BCM 내부 구현은 ECU 요구사항이 아니라 외부 입력 조건·시험 환경으로 구분한다.
- SYS 요구사항에 너무 많은 구현 방법을 적으면 SWE나 SYS.3에서 결정할 자유가 없어진다. 그래도 시험 가능할 정도의 조건은 남겨야 한다.

## CAN으로 '무엇'을 보내는 게 맞을까?

- 스위치의 원시 눌림·해제를 그대로 보낼까, 아니면 ECU가 곧장 이해할 수 있는 조작 상태를 보낼까?
- UNO Q에서 입력 디바운싱과 비상등 버튼 토글 상태를 처리한다. CAN에는 `IGN=ON`, `TURN=LEFT`, `HAZARD=ON`, `BRAKE=ON` 같은 **해석된 운전자 상태**를 보낸다.
- 반면 **램프 점멸 타이밍, 출력 우선순위, PWM, 오류 대응은 STM32가 독립적으로 결정**해야 한다. BCM이 LED를 대신 깜빡이게 하면 Rear Lamp ECU 역할이 애매해진다.

## 이벤트 전송만 할까? 주기 전송만 할까?

- 입력이 바뀔 때만 보내면 CAN 부하가 작고 반응이 빠르다. 대신 ECU가 재부팅했거나 중간 프레임을 놓치면 최신 상태를 다시 모를 수 있다.
- 주기 전송만 하면 복구가 쉽지만, 바뀐 직후 다음 주기까지 기다려야 한다.
- 그래서 **상태 변화 즉시 전송 + 50ms 주기 반복 전송**으로 결론 냈다. 주기 후보 20/50/100ms 중 50ms를 선택했다.
- ECU 입장에서는 유효 수신이 **200ms** 끊기면 오류로 본다. 단순 출력뿐 아니라 통신 장애 감지·복구·재부팅 시 재동기화가 묶이는 설계다.

## CAN 프레임은 하나? 여럿?

- TURN, BRAKE, IGN 등을 별도 CAN ID로 나누는 방식도 생각했다. 하지만 각각의 갱신 주기·타임아웃을 관리하는 부담이 생긴다.
- 이번 규모에는 **`LAMP_COMMAND` 하나에 6개 상태 신호**를 넣는다. 프레임 ID·비트 위치·비트레이트는 SYS.3에서 정하고, SYS.2에서는 의미와 정상/비정상 동작을 정한다.
- 방향지시는 좌우 비트 두 개 대신 `TURN=0:OFF, 1:LEFT, 2:RIGHT, 3:INVALID`로 표현한다. 좌우 동시 활성 모순을 줄이고 잘못된 신호를 시험할 수 있다.
- 유효하지 않은 ID·DLC·값을 가진 **메시지는 전체를 무시**한다. 일부 신호만 몰래 갱신하지 않고 타임아웃도 리셋하지 않는다.

## 통신이 끊기면 램프를 어떻게 해야 하나?

- 마지막 출력을 계속 유지하면 순간적인 통신 오류에 덜 흔들리지만, 브레이크가 계속 켜져 버릴 수 있다.
- 모든 램프를 끄면 구현은 단순하지만 실제 차라면 브레이크등·비상등까지 꺼지는 문제가 있다. 기능별로 안전 상태를 나누는 선택지도 있었지만 **이번 프로젝트에서는 복잡하다고 판단해 뒤로 미뤘다.**
- 그래서 프로토타입 한정으로 200ms 무수신 시 **6채널 전체 OFF**. 이걸 실제 차량의 '안전한 Fail-safe'라고 부르지 않는다.
- 오류를 눈에 보이게 하려고 '모든 후방 LED를 5~10번 빠르게 깜빡이고 끄면?'이라는 생각도 했다. 하지만 그건 다른 운전자에게 가짜 제동·후진 신호를 보낼 수 있는 표현이다.
- 결국 **별도 진단 LED(Blue Pill PC13 온보드 LED 후보)를 5회 점멸**시키는 방식이 훨씬 간단하고 램프 기능과도 분리된다. 점멸은 `HAL_Delay()`보다 비차단 타이머로 처리해 복구 수신을 막지 않기로 했다.
- 진단 LED의 **정확한 ON/OFF 간격**, 부팅 뒤 첫 유효 프레임을 받기 전 200ms 정책은 추후 경계조건으로 확인할 항목이다.

## ECU가 재부팅되면 비상등 토글은 사라질까?

- 비상등이 켜진 상태에서 STM32만 리셋하면 어떡하지? STM32가 자체적으로 토글 상태를 소유하면 동기화가 꼬인다.
- 상태 소유자는 UNO Q. STM32는 초기화 중 램프 OFF로 두고, BCM이 반복 전송하는 **첫 유효 상태 메시지**를 받으면 다시 비상등을 점멸한다.
- 재전송 요청 프레임을 만들 수도 있었지만 50ms 주기 메시지만으로 복원할 수 있으니 추가 프로토콜은 넣지 않기로 했다.

## 비상등을 껐을 때 방향지시등은?

- 좌회전 레버를 유지하고 비상등을 켰다가 끄면 좌측 점멸이 자동으로 돌아와야 하나? 레버를 다시 움직이게 해야 하나?
- **현재 레버 상태로 자동 복귀**를 선택했다. 비상등은 다른 명령을 '삭제'하는 게 아니라 출력 우선순위만 선점한다.
- 새로 활성화되는 점멸은 ON부터 시작한다. 정상 연속 점멸은 **ON 400±20ms, OFF 400±20ms**로 측정한다.

## 미등 밝기 20%가 무슨 뜻이지?

- 공용 램프에서 미등과 브레이크등을 어떻게 구분할까? 별도 LED를 늘리는 대신 PWM으로 구분한다.
- 미등은 **PWM 듀티 20%(허용 18~22%), 1kHz(허용 950~1050Hz)**. 브레이크가 들어오면 100% 출력이고 CHMSL도 켠다.
- 듀티 20%는 '눈으로 보기에 밝기 20%'라고 말하면 안 된다. 실제 검증은 PWM 파형의 듀티·주파수와 진리표로 한다.

## 스위치를 누른 뒤 몇 ms에 켜져야 하지?

- ECU가 CAN을 받은 뒤 반응하는 시간과, 운전자가 실제 스위치를 조작한 순간부터 램프가 바뀌는 시간은 다르다. BCM 디바운싱·CAN 전달 시간이 사이에 들어간다.
- 전체 응답시간만 보면 어느 단계가 느린지 찾기 어려워서 **ECU 내부 10ms, 스위치→LED E2E 50ms**를 각각 목표로 정했다.
- 측정 기준은 정상·무고장·실제 출력 변경이 있는 신규 명령. 점멸 중 OFF 반주기, CAN 두절 상태까지 한 숫자로 섞지 않는다.

## 실제 고장 검출을 구현할 수 있나?

- 전류 센서로 실제 LED 단선·단락을 찾는 방향은 별도 회로와 검증이 필요하다. 지금 단계에서 진단이라는 말을 쓴다고 실제 고장 검출 기능이 생기는 건 아니다.
- 시험 전용 UART로 **가상 채널 고장 주입**, 대상 채널만 강제 OFF, CLEAR 후 복귀하는 수준으로 좁혔다.
- 최근 오류 **16건을 RAM 원형 버퍼**에 남기고 리셋 때 소멸한다. UDS/DTC와 비휘발성 저장은 이번 범위 밖이다.
- 사용한 기술보다 '진짜 검증 가능한 범위를 구분했다'는 설명이 중요하다.

## 문서와 커밋을 왜 다시 손봤지?

- SYS.2 초안은 요구사항·CAN 아키텍처를 한꺼번에 넣어 두어 단계가 흐려졌다. SYS.1도 세부 구현 수치가 너무 빨리 들어오려 했다.
- STK↔SYS가 실제로 연결되는지, PASS 조건이 숫자로 쓰여 있는지 확인했다. 간단한 표가 문서 앞부분에 있어야 전체 맥락이 바로 보인다.
- 이미 만들어 둔 초안 커밋을 그냥 두는 대신 이력을 백업하고 **SYS.2를 통신 / 램프·성능 / 진단·검증의 3개 의미 있는 커밋으로 재구성**했다.
- 문서를 예쁘게 만들기보다, 나중에 '왜 이렇게 했냐'고 물었을 때 당시 선택지를 설명할 수 있는지가 더 중요하다.

## 아직 잊으면 안 되는 질문

- 실제 UNO Q CAN 인터페이스에서 어떤 핀·트랜시버를 쓰는가? 두 CAN 노드 물리 계층과 종단은 어떻게 연결되는가?
- CAN ID·DLC·신호 비트 배치·비트레이트는 어떻게 잡는 게 가장 검증하기 쉬운가?
- STM32 GPIO/PWM/USART/CAN 핀 충돌 없이 6개 출력을 배치할 수 있는가?
- 진단 LED 반복 속도와 최초 CAN 수신 전 타임아웃을 어떤 정책으로 문서화할 것인가?
- SIL과 HIL에서 ECU 10ms·E2E 50ms, PWM, 200ms 타임아웃을 무엇으로 실제 계측할 것인가?
